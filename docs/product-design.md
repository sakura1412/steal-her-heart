# 通用研究引擎与行业扩展：产品规则修订

版本：0.30.0；日期：2026-11-04；状态：开发设计，待实现与验收。基线是仓库 0.29.0 开发草案及当前代码，不代表线上产品或已批准的业务研究范围。本轮只修订规范，不改变 Python API、状态机、持久化 Schema 或历史测试结果。

## 变更及依据

用户本轮提出的八项方向是设计输入；代码现状来自本地检查。降低填写负担、提高分析价值和扩展效率是待验证目标，尚无用户实验或生产效果数据。

| 变更 | 原规则／风险 | 新目标 | 当前实现与迁移边界 |
|---|---|---|---|
| PDT-A 行业适配 | 全行业容易被理解为统一业务字段 | 一套引擎，组合行业维度、工具、分析规则及数据扩展 | 已有通用模板及 SaaS 预设；尚无通用行业包解析器 |
| PDT-B 字段分级 | 默认 21 个核心字段可能过多 | 21 项作为候选目录，按任务明确必选、推荐、可选 | 已支持显式核心子集；不传子集仍默认全部，不能声称默认已改变 |
| PDT-C 动态推荐 | 15 个模块易全量叠加 | 按目的、决策问题、适用性和预算选择 | Markdown 库不被 Python 自动加载 |
| PDT-D 按需访谈 | 固定 11 题阻塞当前问题 | 只问影响当前请求的信息，其他留待需要时 | Python 仍固定 11 题，现有项目 ready 条件保持 |
| PDT-E 分类关系 | 四类互斥会丢失竞争关系 | 同一实体多标签，各标签独立说明依据 | 当前 DiscoveryCandidate.tier 是单值，需版本迁移 |
| PDT-F 读者决策 | 只在报告末端更换文风 | 读者改变规划和分析重点，共享事实 | 当前只有视图契约，没有实际分析／报告执行器 |
| PDT-G 简报语义 | 周期窗口与定时执行混淆 | 即时简报与定时监测分离 | 当前 `/brief` 解析要求周／月周期；无调度器 |
| PDT-H 范围修订 | 改维度可能覆盖锁或全量重跑 | 不可变范围版本、影响分析与差量执行 | 已有锁拒绝覆盖；增量研究仍是设计 |

## 一套引擎，五个组成部分

| 组成 | 负责什么 | 不得改变什么 |
|---|---|---|
| 通用研究引擎 | 理解、规划、任务调度、采集、Research QA、分析、Report QA、版本和恢复 | 行业包不能另建流程控制权威或绕过质量关卡 |
| 行业维度配置 | 字段语义、适用条件、推荐级别、目的组合、比较单位、证据要求、来源提示 | 不将配置或来源提示当成事实、授权或已采资料 |
| 行业专属工具 | 经统一接口接入可信 Adapter，如规格文档解析或公开渠道资料提取 | 不扩大网络／登录／付费权限，不绕访问限制、预算与故障协议 |
| 行业分析规则 | 指定问题、所需事实、比较前提、计算／推理方法、输出类型与验收条件 | 不能用默认值填事实，不能把方法模板直接当结论 |
| 可扩展数据 Schema | 为行业字段声明类型、单位、约束及迁移方式 | Source—Evidence—Claim 追溯、日期、版本、核验和事实／推断区分保持一致 |

继续采用现有八个角色契约和独立 Research Task／Worker；软件、硬件、消费品不分别建立一套 Agent。行业包可组合，Worker 按实际任务和能力分配，不能仅按行业名称派发拥有任意工具的代理。

目标 IndustryPack 包含 namespace、pack_version、schema_version、适用条件、字段定义、目的组合、工具能力引用、来源提示、分析规则及扩展类型。例子见 [行业包设计样例](industry-pack-examples.yaml)，它不是运行配置，也不被当前 Python 读取。

包使用可校验的数据描述，不执行 YAML 内代码或自动导入插件。工具由可信 Registry 注册；包只能引用当前允许能力。未知能力报告不支持，不能安装代码、伪造采集成功或静默换站。软件相关能力不是消费品任务的默认依赖。

行业不明时可使用通用问题与已确认对象继续；仅当行业差异影响当前问题的解释时澄清。跨业态可以组合：相同语义去重，不同语义保留命名空间和口径；单位、定义、类型或方法冲突须解析后再锁定，不采用“后加载覆盖”。不得仅凭产品名推定行业事实。

## 字段目录、推荐级别与执行要求分开

21 个核心字段是通用候选目录，15 个扩展模块是可选研究素材。所有行业共同必需的是可识别的研究对象、明确问题与范围，以及事实的来源／日期／版本／核验元信息；不是所有行业都必查融资、API、材质或供应链。

| 任务要求 | 选择依据 | 执行与 QA |
|---|---|---|
| 必选 required | 用户明确要求，或回答已采用决策问题不可缺少的适用字段 | 锁入本轮范围；资料不足保留缺口，不能因难找而降级 |
| 推荐 recommended | 行业及目的相关，通常有助于理解，但不是回答必需问题的条件 | 规划时说明纳入与否；纳入后仍有记录和明确完成状态，不静默漏字段 |
| 可选 optional | 专项、额外深度或低相关探索，未主动采用 | 不自动加入范围、启动工具或计入覆盖分母 |

行业目录保存 default_recommendation 与条件规则；Planner 解析为本轮字段的 requirement、selected、applicability、selection_reason 和 provenance。推荐级别不等于排程 P0／P1／P2，也不等于置信度。被用户点名的“推荐”字段会成为本轮必选。

选中推荐项不自动成为必需覆盖分母，但它的未完成、失败或未找到必须可见；其重要 Claim 一旦写入报告，证据要求与必选项相同。若该项后来成为回答承诺问题的必要条件，应在分析前按范围修订升为必选，不能带着缺口出完整结论。Optional 不选中就不进入模板；任何选中字段在完整采集对象中仍恰有一个状态记录。

适用性由字段定义与对象事实决定，不能根据是否搜到资料倒推。已锁必选字段只有有依据的不适用判断或可信用户范围修订才能移出适用分母，并重新核查完整范围；未知、失败、暂不可执行不等于不适用或未找到。coverage=1、无缺口／冲突的既有 PASS 规则不被配置放宽。

推荐过程为：研究目的 → 要回答的决策问题 → 所需事实 → 字段及采集任务 → 分析方法与交付物。未给目的时采用通用概览，不强制追问。研究模式影响预算和建议数量，不能删掉用户明确要求；预算无法覆盖时报告具体不足并处理范围，不以完整报告假装完成。

同一比较组内使用一致字段定义与单位。不同业态可采用比较超集及有依据的不适用记录，或拆成明确的可比组；不能将 API 与渠道数强行排序。行业新增字段使用稳定 namespace＋field_id 标识，核心字段不改义。类型化扩展声明 text／enum／quantity／list 等类型、单位、约束及版本；未知 Schema 拒绝或隔离为未解析数据，不静默丢弃。此为新协议，不能直接向现有严格 Pydantic 对象塞额外字段。

## 访谈从当前请求出发

默认仍是“输入想分析的产品名称”。复用已给对象、目的、市场、读者和约束；实体有歧义先消歧。无需先知道我方产品、建立项目或完成行业问卷。

| 当前请求 | 什么时候才补问 | 不需要先补齐 |
|---|---|---|
| 快速了解一个明确产品 | 同名、产品与公司混淆等影响对象识别 | 我方优势、价格区间、全部读者 |
| 比较报价 | 地区、版本或计费口径的差异会改变答案且上下文不足 | 全部 11 项背景 |
| 建议我方差异化／销售回应 | 缺少必要我方能力或目标客户 | 与该建议无关的项目资料 |
| 最近更新／周报 | 时间窗或对象集合不明确 | 长期监测计划 |
| 可选长期项目 | 为本次问题需要持久记录的背景与约束 | 未来可能用到的全部字段 |

每轮需要问时最多 2～3 个相关问题；只有一个必要缺口就只问一个。用户答不上来可选“先做通用概览”“仅分析公开竞品信息”等有明确限制的路径，不把建议选项自动写成用户事实，也不伪造未知答案。一般画像可以继续，缺关键输入的具体判断仍标缺口。

目标区分 request_ready（当前问题可规划）、profile_draft（可选背景未全）与 profile_complete（完整档案）。三者不等于 research_ready 或 scope_locked。未来项目上下文接口须支持真实缺口并保留来源，旧版严格项目读取器继续拒绝不完整档案；在迁移完成前不能把部分 Markdown 冒充现有 Python ready。固定 11 题转为完整问题池，旧 9／11 题记录仍可读、已答不重问、未答不补造。

## 竞品分类是关系，不是实体身份

候选实体只保留一个 canonical_id；与种子对象的关系保存为 labels[]，可同时为直接竞品、替代品、潜在进入者、行业标杆。每个标签绑定 seed_id、客户／场景／地区／时点、reason、evidence_refs、核验状态及适用的不确定性。分类是有依据的分析，不把用户标签或模型评分伪装成事实。

展示可以选择 primary_label，但不排除其他标签，也不决定重复采集。同一对象在某场景直接竞争、在另一场景充当标杆时，两条关系分别说明。现状／不行动路径必须包含 alternative 标签，不因多标签删掉替代方案。四类覆盖按有效标签并集计算，候选数量按 canonical_id 去重；分类缺口仍明确，不为凑齐四类加标签。

评分按关系与问题说明依据；不同类别不直接比较一个总分。用户可修正标签、对象、名称与依据，原始版本保留。旧 tier 只迁移为一个已知标签，不补猜其他标签；候选内容变化产生新提案摘要，旧批准不能直接授权新版名单。

## 读者改变分析问题，共用事实

Planner 在研究前将所选读者转为 ReaderDecisionSpec：决策问题、所需事实、分析方法、期望决策产物与限制。Analysis 按这些问题产出不同但可追溯的结论；Reporter 只组织已核对分析，不独自创造新策略。角色不限四类，未指定时采用通用概览，不强迫做四份报告。

| 读者示例 | 分析重点 | 决策产物 |
|---|---|---|
| 产品经理 | 用户任务覆盖、可比能力差距、机会与取舍 | 机会排序及验证建议；我方路线图需我方背景 |
| 销售领导 | 可比价格、竞争场景、风险和资源配置 | 优先竞争场景；真实赢输归因需授权样本 |
| 一线销售 | 适配条件、异议依据、比较边界 | 一页卡、探测问题与禁说项；我方优势须双边证据 |
| 运营 | 渠道与内容机制、转化动作、可验证增长假设 | 实验建议及适用边界；不把公开动作当增长效果 |

共用 Source／Evidence 版本及口径，不按角色重复采集；不同问题允许不同 Analysis／Claim。观点差异须解释问题与假设，不能改变同一事实、时间或置信度。新增读者的影响有三种：仅版式变化 → 新报告及 Report QA；现有证据足够但决策问题变了 → 新研究修订和分析版本、采用依据、新 Claim 核查及 Report QA，零新增联网任务也合法；需要新事实 → 按影响集补证及完整 Research QA。不能笼统认为“换读者就沿用旧分析”。

## 即时简报与定时监测

目标 `/brief` 是本次生成简报；对象可由当前有效上下文提供，否则只补问对象或资产范围。可指定“近七天”“月报”等内容窗口；不指定窗口时做基于明确资料时点的即时摘要，不能暗示已刷新到今天。历史材料须检查时效；要求最新信息而材料不足时，按范围与预算规划更新。

“生成一份周报”只是本次输出；“每周一自动监测这些对象并提醒变化”才是持续任务需求。定时监测另行设计、另有明确授权，至少绑定对象／范围版本、频率、时区、预算、有效期限、通知规则与停止方式。普通研究、简报或本规范更新都不创建定时任务，不自动续期；调度器不是本轮或研究 MVP 的隐含依赖。

当前 Python `/brief` 仍要求 weekly／monthly，缺周期返回澄清；裸 CLI `brief` 仍是离线 ResearchBrief 识别器别名，推荐 `recognize-brief`。未来更改路由须显式迁移、保留兼容测试和清晰帮助；本文不发布新的 `/monitor` 命令或不存在的参数。

## 范围版本与变更影响

ScopeManifest 目标记录对象、问题、有效维度及要求／适用性、行业包与 Schema／分析规则版本、读者决策要求、地区／时期、来源约束和证据策略，并形成稳定摘要。包升级不静默改变已锁任务；格式偏好另存，不伪造事实刷新。

每次变更先比较当前基线，输出变更项、影响单元、可复用／重核／重提取／刷新／新采集、受影响比较／Claim／报告片段、预算影响与授权依据。不修改旧锁、不覆盖旧报告。字段语义或单位变化使依赖它的事实与分析重新评估；仅排版不触发重采；删除对象保留历史，重算相关总体比较。未知依赖扩大核查并说明，不能扩大未授权采集。

用户明确完整的增补指令沿用既有授权规则，不多加泛泛确认；有歧义或未授权的扩展才询问。显式项目仍受其名单／最终维度批准约束，新版本不能用旧 token 或旧锁。运行恢复与迟到结果遵循 [状态机 v2](state-machine-v2.md)、[调度](task-scheduling.md) 和 [多轮修订](incremental-research.md)；现有 project_review 拒绝覆盖的行为保持。

## 实施与完成边界

先实现一个纯行业配置与维度解析模块：校验包、组合／冲突处理、按目的生成可解释字段选择及版本摘要，保留旧模板默认行为的兼容边界。通过对应确定性验收后，再分别接入 Planner／范围协议、渐进访谈、候选多标签、读者决策及即时简报路由；每次一个模块，不一次重写所有流程。

工具 Adapter、分析方法执行和扩展证据 Schema 随真实需求逐个接入，各自验收。配置能加载不等于工具或分析方法存在。生产链依然按 [路线图](roadmap.md) 打通；本轮设计检查不替代功能或用户效果验证。验收场景 PDT-01～PDT-16 见 [TASK_SPEC](../skills/steal-her-heart/TASK_SPEC.md)。

# SaaS／工具类研究推荐配置

版本：1；2026-11-04。仅在用户明确选择 SaaS／工具类研究，或本次实际资料确认该交付方式适用时采用。它是全行业维度库上的可选推荐，不把餐饮、硬件、专业服务或混合业态改成 SaaS，也不要求先建立我方项目。

[机器可读配置](saas.json) 给出统一字段、采集优先级、问题、比较条件和数据源提示；同一比较中的对象沿用同一份选定定义。该文件随技能提供，不依赖 Python 安装。Python 的 `preset saas` 只读取对应推荐配置，不启动研究、创建项目、确认名单或生成最终锁。

## 先采什么

| 优先级 | 推荐采集重点 | 为什么先做／何时调整 |
|---|---|---|
| P0 | 定位与目标任务、版本／价格／计费、功能广度与关键任务深度、免费／试用边界及付费触发 | 先判断对象、场景和商业口径是否可比。预算不足时优先保留这些问题的真实来源与缺口 |
| P1 | API 与集成生态、迁移及数据锁定、近期迭代、分层用户评价 | 解释落地成本和长期使用边界，交叉核对宣传与具体任务体验 |
| P2 | 代表客户，以及与场景有关的安全、合规、治理 | 仅在目标客户和研究目的需要时展开；企业治理可按用户目的上调优先级 |

P0／P1／P2 是本配置的工程建议，不是某类产品必须具备的能力，也不是证据可信度分数。没有公开 API、免费版或某认证时，先核实公开材料；未提及仍为缺口，不能直接写成“不支持”。明确不适用须保留理由。

当前推荐包含15个所选通用字段和10个专项字段，共25个字段，每个字段都有采集定义；不修改全行业默认的21个核心字段。

| 优先级 | 配置中的字段 ID |
|---|---|
| P0（11项） | positioning、target_customers、core_offering、delivery_usage、offer_variants、prices、billing、trial_experience、feature_breadth、feature_depth、free_conversion_path |
| P1（12项） | value_proposition、limitations、positive_reviews、negative_reviews、recurring_complaints、recent_changes、api_maturity、integration_maturity、data_portability、switching_cost_analysis、release_cadence、review_sample_context |
| P2（2项） | reference_customers、security_governance |

## 六类重点的采集口径

| 重点 | 具体要回答的问题 | 典型比较条件与证据要求 |
|---|---|---|
| 功能广度与深度 | 广度：覆盖哪些客户任务、对象和交付步骤？深度：同一关键任务能完成到什么程度，哪些权限、批量操作、自动化、异常处理或规模限制影响结果？ | 先列一致的任务清单，再给文档中的可完成步骤和限制。营销页功能数量不是深度分数，某版本有功能也不等于所有版本可用 |
| API 与集成生态成熟度 | API 的认证、额度、分页、Webhook、版本及弃用策略、SDK／示例如何？集成是原生、第三方还是自建；支持哪些对象与读写方向，由谁维护？ | 对齐版本、权限、套餐、调用单位、对象和维护主体。集成目录中的一个 logo 不证明双向同步、全对象覆盖或稳定可用 |
| 免费策略与转化路径 | 免费层、试用期、使用／席位／容量限制是什么？引导用户如何达到价值，哪些限制或场景触发升级？ | 保存地区、版本、试用资格、计费周期和升级规则。公开引导动作与实际转化率分开；没有内部数据或可靠来源，不估计转化率、留存或收入贡献 |
| 切换成本与数据锁定 | 能导入／导出哪些对象与格式？可否通过 API 批量取回数据，附件、关系、历史和权限是否保留？删除、迁移工具、合同及学习成本如何？ | 区分文档可核实的导入导出、删除与合同条件，以及依据这些事实作出的迁移难度推断。没有进行迁移实测时说明未实测，不能把“有导出”当成“无锁定” |
| Changelog 与迭代速度 | 明确窗口内发布了哪些功能、修复、API 变化和弃用？哪些版本、地区或用户可用？ | 记录发布／生效日期和版本，区分功能、修复与公告。发布次数、提交次数和用户价值是不同指标；无法穷尽历史时披露实际覆盖窗口，不把未找到公告当成没有迭代 |
| G2／Capterra 等评价样本 | 不同评分段、角色和公司规模用户分别提到了什么；评论是否有激励、验证标签或厂商回应？ | 逐条保存评论链接、发布日期、获取日期、评分、公开角色／规模标签、激励／验证标记和原文。记录选择方式及分母；不足样本和不可得字段保留缺口 |

## 典型数据源清单

先确认产品实体和官方域名，再发现实际页面。以下是入口和查找方向，不是已采集事实；不要按猜测的 slug 拼出产品、评论或文档链接。

| 来源 | 优先查什么 | 使用边界 |
|---|---|---|
| 产品官网、功能页和帮助中心 | 定位、关键任务、版本支持、功能使用步骤与限制 | 标为官方宣称；文档所述行为与实测结果分别记录 |
| 官方定价页、计费／套餐文档、试用说明 | 价格、计费单位、地区、免费层、试用与升级触发 | 获取日期逐条附着，保留税费、折扣、周期和资格条件；无法直接访问则记受限 |
| 官方开发者门户与 API 文档 | 认证、额度、对象、读写、Webhook、版本、SDK、弃用 | 文档入口与实际端点版本要一致；不因存在文档就声称端点已调用成功 |
| 官方集成目录与集成方文档 | 原生／第三方／自建、对象覆盖、方向和维护主体 | 两边文档可相互对照；厂商、转载和同一合作公告不自动算独立证据 |
| 导入／导出、迁移、删除与合同文档 | 数据可携带性、丢失项、保留期、退出与续费条件 | 事实与迁移成本判断分开；合同须核对适用主体、版本和地区 |
| 官方 Changelog、版本公告、状态页 | 发布、生效、修复、弃用与运行事件 | 状态页反映所覆盖服务的事件，不等于完整发布记录；窗口和缺失记录要明确 |
| [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases) | 与产品实际相关的公开仓库版本和发布说明 | 仅在存在可核对关联的公开仓库时采用；开源仓库版本不能直接当成全部云服务部署历史 |
| G2／Capterra 具体产品评价页 | 可访问的公开评价与样本元信息 | 本配置没有接通两站采集器。访问受限即停止；不能把受限页面计为没有评价，也不自动换入口绕过 |

G2 的评论分发 API 面向合作伙伴并需要专用密钥，不能把其文档当成已可用的免密采集渠道。[G2 官方说明](https://documentation.g2.com/partners/docs/get-started-with-g2-review-syndication/) 支持这一接入限制。Capterra 说明其收集激励和非激励评论，因此采样需保留相应标签；平台审核也不等于每条体验可推广为客观产品事实。[Capterra 官方说明](https://www.capterra.com/resources/how-we-verify-reviews/)

## 评价采样建议与机械检查

默认建议观察最近365天，分别在 G2 和 Capterra 的低、中、高评分段收集样本，每个平台每段目标3条。这是有限研究的起点，不是统计代表性保证；实际产品规模、渠道可用性和用户目的可要求另一套显式策略。低／中／高分段按当前配置和检查器定义，不把不同量表直接混算。

采样时保留以下记录：

- 每个平台的实际访问结果、检查日期、产品身份匹配和缺口说明；未采集、查找后未找到、访问受限分别记录。
- 每条评论的可定位链接、原文、发布日期、获取日期、评分、公开角色与公司规模，以及可见的激励、验证标签。不可得字段显式记未知，不推测匿名评论者的背景。
- 评论的选择顺序、评分分层、实际样本数与可见总量，区分平台整体评分、所选样本和具体抱怨出现次数。
- 同链接去重，并标出跨页面、跨平台相同文本的疑似重复；两个域名不自动代表两份独立体验。疑似重复需核实，不能简单翻倍计数。

按评分段主动选样会改变样本分布，不能用该样本的均值、正负比例或少量重复意见推断总体评分、普遍投诉率或赢输原因。低评价不等于已证实缺陷，高评价也不证明效果普遍成立。

Python 的 `preset saas --review-sample FILE --as-of YYYY-MM-DD` 只对用户提供的数据执行元信息、时间窗、重复和分层覆盖检查；两项参数必须同时给出。它不登录评价站，不抓取评论，不验证链接里的原文，也不判定观点是否支持结论。结果保持 `facts_validated=false`，不会发出 Validator 的 `PASS`。即使采样覆盖完整，仍须逐条核对来源、引文、语义、适用范围和冲突。

输入 JSON 使用 `records`、`platform_attempts` 和固定的 `rating_scale="1_to_5"`。下例只展示字段，所有元信息尚未知、平台也未检查；占位记录不会计入有效覆盖，不是一条实际评价：

```json
{
  "rating_scale": "1_to_5",
  "records": [
    {
      "id": "sample-placeholder",
      "platform_id": "g2",
      "review_url": null,
      "published_on": null,
      "acquired_on": null,
      "rating": null,
      "role": null,
      "company_size": null,
      "incentivized": null,
      "verified": null,
      "text": null
    }
  ],
  "platform_attempts": []
}
```

实际评论填入原链接、`YYYY-MM-DD` 日期和1～5评分；低分为不高于2分，中分为大于2且小于4分，高分为不低于4分。不能把10分制直接填进来。布尔 `false` 表示已知为否，`null` 才表示未知；角色、规模等不可得时不要猜测。

每个平台最多一条检查汇总：`platform_id`、`outcome`、`source_url`、`acquired_on`、`scope` 和可选 `note`。`outcome` 可为 `checked`、`unavailable`、`not_found`、`not_applicable`；非 `checked` 必须说明 `note`，`scope` 写真实对象、观察窗及排序／过滤范围。没有实际查找就不填“未找到”，没有实际访问就不编访问结果。重复链接中的 fragment 可能定位到单条评论，不能一律删掉；相同规范文本只作为疑似重复，计数一次并待人工复核。

配置读取成功退出0；带样本时，机械覆盖完整退出0、有缺口退出3、参数或JSON无效退出2。这里的0只表示该次配置／样本操作成功，不能解释为研究完成或 Validator PASS。

## 接入研究与项目评审

默认单对象研究可选择本推荐中的相关字段，不增加项目背景、名单或维度确认的前置要求。可选项目若采用预设，仍需把选定字段写成该项目的正式提案，经过已有名单／维度评审与最终锁定流程；优先级、源提示或预设散列不代表用户批准，也没有自动绑定进旧的锁。

本配置和样本检查只加强可检查的研究准备。Research 调度、逐条来源与事实支持核查、完整 Validator、分析和报告仍未接通；不能把读取配置、通过结构检查或凑齐样本数当成研究已经完成。

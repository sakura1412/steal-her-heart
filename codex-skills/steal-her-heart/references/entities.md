# Entity Management / Entity Resolution

研究对象先解析为有稳定身份的实体，再开展资料采集与分析。Competitor 表示特定问题下的竞争关系，不是所有对象共用的一种实体类型。本文件定义 Codex 的工作方法和记录约定，不代表已部署实体数据库或自动消歧服务。

实体类型与身份记录是通用基础，业务研究维度仍按对象、行业属性和用户目标动态生成。只解析当前判断需要的关系，不要求每次建立完整企业图谱。

## 实体类型

| 类型 | 含义及身份边界 |
|---|---|
| Company | 企业主体；集团与具体法人分开识别，名称相近或同集团不等于同主体 |
| Brand | 品牌；与所有者、运营者、商标权利人分别建立有依据的关系 |
| Product | 产品或产品系列；不能与生产企业、品牌或具体版本混为一体 |
| Product Version | 产品版本／版次；属于具体产品，区分版本名称、发布日期和有效条件 |
| Service | 服务供给；服务名称与运营机构分开，明确服务范围 |
| SKU | 商品规格／交易单元；标识限定在发行者或商家命名空间内，不跨卖家仅凭编码合并 |
| Platform | 平台；区分平台本身、运营主体及平台中的商品或服务 |
| Organization | 非企业组织或其他组织主体；Company 是更具体的组织类型，不能为同一主体重复建节点 |
| Person | 与研究问题有关的公开角色人物；只使用必要的公开职业信息，角色与任职关系有时间范围 |
| Market | 市场；明确地理、客户或交易边界，不能只凭同名标签合并 |
| Industry | 行业分类；记录定义、分类体系及适用时期，不能把不兼容分类直接等同 |
| Channel | 销售或分发渠道；具体渠道与渠道经营主体区分 |

类型允许按需扩展，例如需要独立维护客户群体时可定义 Customer Segment 并写明含义。不能为凑类型创建没有证据的节点。同一现实对象确有多重类型时，以一个身份加有依据的类型说明表示；名字相同但身份不同则使用不同实体。

## 最小实体记录

在当前任务中分配与名称无关的稳定 entity_id。改名、翻译或显示名称变化不重发身份标识；跨任务复用须先核验旧映射，不能仅按字符串命中。

实体记录包括 entity_id、类型／定义、显示名称、原文名称、别名与语言、可用的外部标识及其命名空间、识别依据、身份状态、记录版本及来源引用。没有可用外部标识可以留空，不能生成虚假注册号或型号。

别名分别标明正式名称、旧名、译名、简称、商标名或搜索线索，并记录来源、适用地区和时期。自动翻译、音译、缩写相同只能生成匹配候选，不能自动证明同一实体。网址和账号可以辅助识别，不能单独证明法人身份、所有权或产品归属。

身份状态区分待核验、已解析、存在歧义／冲突及已被合并或拆分的历史记录。已解析必须有足够证据说明本轮资料确实属于该对象，不表示所有属性均已核验。来源的发布者与内容描述的对象分别记录，不能把发布者默认当成事实主体。

## 消歧步骤

1. 保留用户原始名称和上下文，列出可能层级，不先假定“名称＝公司”。
2. 获取与当前对象有关的身份材料，比较主体标识、产品归属、地区、语言、经营范围、时间及上下级关系。
3. 同名、别名、多语言名称分别提出候选匹配，记录支持与反对证据。企业收购、改名和授权经营不能仅靠名称推定延续或同一主体。
4. 有足够证据时绑定 entity_id；仍无法确定且会影响判断时，给少量候选并补问地区、具体产品或一个可核验入口。用户的选择确定研究意图，不自动验证所有外部身份事实。
5. 在歧义解决前隔离候选资料，不混填价格、规模、口碑或客户数据。仅有不受歧义影响的独立部分可继续。

用户输入品牌时，核验品牌与所属／运营主体的关系，按相关材料识别主要产品或服务。只展示实际核验部分，不声称产品线完整。此处建立必要上下文，不自动对每个旗下产品启动全面研究；用户明确指定某产品或版本时，不用品牌平均数据代替。

## 关系记录

关系使用有方向的 subject_id → predicate → object_id，记录 relation_id、关系版本、具体含义、来源／证据定位、核验状态、置信依据与上下文。上下文按需包含市场、渠道、客户群体、产品范围和适用场景。

常见关系可表示拥有品牌、运营品牌、提供产品／服务、版本属于产品、规格属于产品或版本、运营平台、通过渠道销售、服务市场、属于行业、供应、合作及竞争。关系类型可扩展，但必须定义方向和语义；不能用笼统的“关联”掩盖已知关系，也不能从“相关”推导所有权。

所有权、运营、授权销售和合作不是同一种关系。公司可同时是供应商、合作伙伴和竞争者，分别记录各关系的产品范围、市场、时间和证据；不能因为角色重叠就强选一种。竞争的四类标签绑定具体实体对及场景，不作为实体全局属性。

关系支持一对多、多对多和共同所有。不得从母公司关系自动推导子公司拥有关系，也不得将品牌或公司的事实自动向全部产品、版本、SKU 传播。任何推导关系必须标为推断、列出前提并核查，不能伪装成来源直接陈述。

## 时间与历史

区分 valid_from／valid_to（关系实际生效区间）、published_at（材料发布日期）、collected_at（本次取得日期）和记录版本时间。未知生效日期保留未知；获取日期不证明关系从该日成立，未见终止日期也不证明永久有效。

证据仅说明某时点关系时，记录“截至该材料时点观察到”，不编造连续有效区间。查询当前关系须核时效，历史分析采用对应时期关系。收购、品牌转让、渠道调整等变化追加关系版本；相互冲突的材料并列保留，未解决前限制结论。

## 事实归属、市场与报价

每条 Evidence 指明事实主体 entity_id、实体记录版本及适用的使用端／版本／规格／市场／渠道／时期。Web、App、小程序、桌面、线下按本次范围分别核查；使用端与销售渠道或资料来源平台不是同一属性。公司营收、品牌口碑、产品能力、某版本限制和某 SKU 售价不能互相代替。

价格通常是特定交易条件下的观察值，不是 Product 节点上的唯一标量。记录相关产品／版本／SKU、市场、销售方、渠道、币种、计价单位、周期、税费或优惠条件以及获取日期；未知条件保留缺口。同一产品不同国家或渠道的报价分别保存，不能覆盖成一个“当前价格”。

是否将地区版建为独立版本，依据产品实际差异；仅价格不同可共用产品身份并保留不同报价上下文。不同市场、时期或规格的价格差异不自动构成证据冲突；同条件互斥陈述才进一步核查。比较时对齐条件，不可比则分别呈现，不擅自折算或排序。

实体和关系都可沿 Evidence → Source 回溯原文；反向能定位采用它们的分析结论与报告部分。资料身份、关系或版本变化时，重新评估受影响事实、比较和结论，不能只改显示名称。

## 合并、拆分与纠错

合并只针对经证据确认属于同一实体的重复记录，不能把品牌和公司、产品和版本、集团和子公司作为“去重”合并。记录操作标识、输入与结果实体版本、理由、证据及影响范围；保留旧标识、旧名称和历史映射，不删除来源或旧报告。

拆分用于发现原记录混入多个实体的情况。为独立对象建立各自身份，记录从旧记录到新记录的映射；每条事实按归属依据重新分配，无法分配的放入待消歧区，不复制到所有新实体。关系端点也须重新核对。

同一纠错操作不重复执行；取消错误合并时保留纠错历史。新分析采用新版本，历史报告仍引用原版本并可注明更正；受影响的比较、结论及报告必须重新核查。用户明确纠正研究对象可作为范围指令，但不把未经核验的所有权陈述当已证实事实。

## 在 Codex 中记录与交付

简单单对象任务在研究说明中保留已核验身份及必要关系即可。关系复杂或需要保存时，可在本次研究目录中按需维护 entities.md、relations.md 和 identity-changes.md，使用稳定 ID 与来源定位；不要求用户先建项目。

保存前核对实体引用、关系两端、证据定位、时间和版本。仅生成结构或写出文件不等于已消歧；没有实际文件操作时在对话里记录，不声称数据库或跨任务身份服务已建立。

交付时明确本次分析层级、地区／渠道／版本边界、身份未决项及已核验关系。对缺证关系写未知，不为了画完整图谱补造节点或边。

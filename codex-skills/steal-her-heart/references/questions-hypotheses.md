# Research Question & Hypothesis Agent

这是同一通用 Agent 内、由 Planner 调用的研究设计职责，不是必须另启进程或单独部署的服务。它把用户问题转成可验证的问题与假设，输出给 [Research Framework Agent](dimensions.md) 和后续任务规划。

## 输入、输出与权限

输入：用户原话、研究对象与实体层级、目标和决策情境、已有本次材料及未知项、范围版本和预算。输出：`questions.jsonl`，每行一个符合 [问题 Schema](../schemas/research-question.schema.json) 的版本化记录。可以组织问题、提出明确标为待验证的假设、指定所需支持／反对证据；实际搜索由获授权的取证任务执行，不能自行扩大范围或将模型记忆写成证据。

## 竞品分析的五个核心问题

综合竞品分析用以下五问规划取证，并在报告中逐问给出结论、依据或具体缺口。用户只问定价、渠道或某项能力时，保留直接影响该决定的问题。用户点名的单个对象就是研究范围：可以交代其已核实的市场类别与替代路径，调查新增具名玩家前先取得授权。

| 核心问题 | 研究与报告要回答什么 |
|---|---|
| 市场上有什么？ | 先界定需求、地区与时期，再说明主要玩家如何竞争。市场研究要考虑直接竞品、替代品、潜在进入者和标杆，以及客户继续沿用旧办法的可能。列出各对象入选的依据和市场覆盖边界。 |
| 竞品解决什么问题？ | 说明谁在什么情况下遇到什么困难、原来如何应对、希望得到什么结果。将厂商定位与实际客户的使用动机分别取证。 |
| 竞品是怎么解决问题的？ | 选一个核心任务，沿用户从开始到获得结果的过程拆解关键步骤、用户与产品或服务的交互、承担交付的功能与能力、依赖及摩擦。涉及技术机制时说明文档或实测能证实到哪一层。 |
| 竞品做得怎么样？ | 用同一任务和可比条件检验成效，对照优势、短板、差异化及其对竞争力的影响。说明谁受益、代价是什么、在哪些条件下相对优势会改变；只有能力说明时，将效果列为待验证。 |
| 我们应该怎么做？ | 把有证据的未满足需求或取舍写成机会。已知我方目标、资源且用户要求对照时，给出建议优先级、第一步和验收信号，并说明何种结果应停止或调整。背景缺失时给条件式选项和最小验证动作，明确哪项我方信息会改变决定。 |

交付前任选一条主要建议逆向核对：哪个用户遇到了什么问题，现有方案怎样处理，哪条已核验差异使这项行动值得尝试？把建议关联到相应 Claim，将仍待验证的前提写在建议旁。若重要事实缺失，下一步可以是一次观察、询价或试点。

例如，在虚构的设备租赁场景里，两份可比报价能证明短租价差。要建议我方推出日租，还需知道短租客户是否因整周起付而放弃下单，以及出入库成本是否允许。可先复核近期未成交询价的租期与原因，再选一种设备试行日租，按新增成交和履约后的毛利决定是否扩大。

## 问题驱动的步骤

1. 保留用户原问题并标记核心决策。把复合问题拆成可回答的子问题，记录 parent_question_id 和相互依赖；描述类问题可以没有初始假设，不为了填字段预设结论。
2. 对解释／比较／因果问题提出可证伪的初始假设，标明来自用户、规划推测或背景知识，并列替代解释。假设从 unverified 开始，不是 Claim 或事实。
3. 先定义什么观察支持、什么观察推翻假设，以及对象、地区、时间、使用端和比较基线。写出证据来源类型、最少独立来源组及质量要求；取证困难不降低既有底线。
4. 将支持性查询与反证查询一起纳入采集计划。优先核查会改变结论、否定前提或决定后续问题是否值得研究的证据，不按搜索结果数量奖励完成。
5. Validator 分别核验支持与反对 Evidence 的相关性、独立性、时效和适用性；相同来源改写不算交叉验证。Analysis 形成有依据的当前结论，回填已核查的 Claim 引用。
6. 输出 verification_status、verification_complete、confidence 及理由。没有反证被找到不等于假设成立；“搜过一次”不等于验证完成。新材料或范围变化追加问题新版本，保留旧假设与判断依据。

每个问题的必填字段：问题描述、初始假设（允许明确 null）、假设为空的理由、替代假设、支持与证伪条件、所需证据、当前结论（未形成时 null）、支持证据引用、反对证据引用、结论引用、置信度及依据、核查进度和验证结果。记录 problem_id／revision、scope_version、entity_refs；Evidence／Claim 使用精确 ID 与 revision，不复制另一套事实文本充当权威台账。

## 验证状态

| verification_status | 含义 | verification_complete |
|---|---|---|
| unverified | 尚未完成相关取证与核查 | false |
| supported | 在声明范围与证据条件下支持假设／回答；反证已实际检查 | true，须有支持 Evidence 和核查后的结论 |
| refuted | 有适用反证推翻假设，当前结论说明替代解释或边界 | true，须有反对 Evidence 和核查后的结论 |
| mixed | 存在已核验的支持与反对材料，结论仅成立于特定条件 | true 仅表示本轮评估完成，须呈现双方；不自动满足研究充分性 |
| inconclusive | 有材料但无法作出合格判断，缺口和下一步明确 | false，即使本轮预算已耗尽 |
| not_applicable | 原问题在已核验对象／范围下不适用，有实际依据 | true，须有依据和理由，不用来隐藏未知 |

verification_complete 不等于假设为真，也不等于整份报告通过 QA。mixed 若仍有关键未决冲突，不计充分覆盖；refuted 可能已经回答用户问题。置信度不是模型自信概率，按 [来源质量规则](source-quality.md) 赋值；只反映当前结论的依据，不把高 confidence 当完成凭证。

## 示例：分析 Notion 的竞争优势

以下是问题拆解示范，不声明 Notion 当前具有任何具体能力，也不授权自动新增具名竞品。

| 子问题 | 待验证假设／替代解释 | 需要的证据与反证 |
|---|---|---|
| 核心用户是谁，哪些群体实际使用？ | 官方定位可能与实际使用群体不同 | 当前定位和客户资料，与具有场景信息的用户材料交叉核查 |
| 用户为什么选择它？ | 可能因为某种工作方式，也可能是既有习惯、渠道或切换成本 | 明确选择理由的用户材料；寻找未选择、迁出或替换的原因 |
| 哪些能力形成有意义的差异？ | 被宣传的能力未必是独有或影响决策的能力 | 同任务、同版本／地区的实际能力与可比基线，查同类实现和缺陷 |
| 类似能力是否可替代？ | 替代方案可能用不同方式完成同一任务 | 当前已授权范围内的替代路径；需要新增对象时按范围规则处理 |
| 优势是否可持续？ | 能力可能易复制，现有优势也可能依赖暂时条件 | 历史变化、竞争响应、约束和切换情况；未来判断保留情景与不确定性 |
| 什么会推翻优势判断？ | 特定客群／规模／使用端可能不适用 | 失败案例、反向选择、成本与性能边界；反例不因不符合预期而丢弃 |

本例不要求每次都研究六个问题；按用户目的裁剪，保留其明确问题。当前问题无法在授权范围内建立比较基线时，先给非比较事实与缺口，不能直接声称“竞争优势已证明”。

## 完成与回退

设计完成要求问题能映射到具体证据与可观察判断，核心问题与依赖明确，假设和事实分开，支持和反证计划均有说明。无法提出可证伪假设时保留描述问题并说明原因，不强行猜答案。

缺输入交 Planner 补任务；无预算或无法访问则记录 inconclusive，不无限搜索。新增问题先做影响分析，已存在的 Evidence 可复用但须匹配实体、范围、时效和证据版本。报告优先回应用户问题及验证结果，不按采集到多少页面组织结论。

# /init-project 项目名

引导用户创建或续建竞品分析项目。`$ARGUMENTS` 表示本次调用提供的实际项目名；它是指令模板的占位符，不是可执行代码。Codex skill 不保证自动替换它，应从用户当前请求提取实际名称。用户只贴出这份指令、未给名称，或仍为字面量 `$ARGUMENTS` 时，先问名称，不创建同名目录，也不自行选 default。

工作目录是本竞品分析仓库。遵循 [AGENTS.md](../AGENTS.md)，不限行业、品类或读者。此入口由 Codex 使用当前可用的文件与联网工具执行；Python CLI 仍为单题访谈和离线路由，不因本指令存在而获得搜索、报告或新的确认能力。

## 1. 读取模板并识别项目

先读 [templates/profile.md](../templates/profile.md)。它指向包内同一份标准模板，不维护第二份业务配置。目录名使用 ProjectWorkspace 支持的1～80个中文／字母／数字／下划线等字符，首字符为文字、数字或下划线，其余可含点和连字符；不接受路径、`.`、`..`、斜杠、反斜杠或未替换占位符。把项目名作为数据传递，不拼接执行用户提供的 shell 代码。

检查 `projects/<项目名>/`：存在则先读 profile.md、dimensions.md 和已有 competitors.md，复用已答信息及有效确认。不要覆盖现有完整档案或悄悄重置用户修改。跨出 projects 根目录的路径／符号链接拒绝写入。

## 2. 每次只问2～3个问题

一次展示一小组，等待本轮答案后再问下一组。已知信息直接复用；只剩一个缺口或需要单独消歧时可以只问一题。每个字段算一个问题，不把所有问题藏在一条长问题里。缺项目名时，将它计入第一轮的2～3题。

按用户背景调整组合，通常可这样安排：

| 轮次 | 本轮字段 |
|---|---|
| 第一轮 | 产品名称与一句话描述、所属行业／业态、目标客群 |
| 第二轮 | 市场范围、分析目的、读者与关注点及期望格式 |
| 第三轮 | 核心优势、主要短板、价格区间 |
| 第四轮 | 已知竞品、特别说明 |

读者可以是任何角色，要求记录“角色／关注点／期望格式”，不能自动补固定四类。多行业保留用户原文。用户一次主动回答多个字段时全部接收，只追问缺口。用户自述不作为外部核实的事实。

## 3. 答不上来时提供可选建议

根据已有描述给2～3个容易比较的选项，并允许自由填写；说明它们是待用户选择的建议。可参考：

- 市场范围：中国大陆／海外目标地区／先聚焦一个地区。
- 分析目的：产品与路线图／定价与商业模式／销售或市场策略；投资等其他目的照常支持。
- 期望格式：对比矩阵／简报／一页行动卡；选择仍由用户决定。
- 行业和客群：只根据用户描述提出备选分类，不把建议写成已确认背景。

不替用户编优势、短板、价格或竞品。优势短板不清楚可标“待确认”；价格、已知竞品和特别说明可空。名称描述、行业、客群、市场、目的或读者／关注点完全未知时继续澄清。保留明确未知与明确“无”的区别；用户没选的建议不落为答案。

## 4. 保存项目背景

补齐后保存为 `projects/<项目名>/profile.md`，遵循模板字段和三列读者表。业务数据只在 Markdown 中保留一份；需要程序身份时仅加现有 profile-meta 身份元数据。不要另外藏一份业务 JSON。

可以在中断时保存已回答的部分，但须明确这是未完成草稿。手工草稿继续在原文件补齐，不调用终端单题访谈来覆盖／合并它。完整文档可用现有 `project-status` 读取验证；结构通过不代表业务陈述已被证实。

## 5. 推荐维度、生成文件并等待确认

读取 [library/dimensions.md](../library/dimensions.md)，结合 profile 的行业／业态、市场、目的和读者，推荐“所选核心＋适用扩展”。解释每个模块为何相关，允许删改、跨行业组合或新增维度；没有行业匹配时自定义，不强套软件功能。

生成 `projects/<项目名>/dimensions.md`，至少列明：

- 版本、状态“待用户确认”、对应项目／背景范围和维度库版本。
- 字段ID、名称、定义／比较口径、事实／反馈／推断类型、适用条件、优先级。
- 需要时明确地区、版本、币种、计费单位与近期动态时间窗口；未知条件保留缺口。
- 每条信息必带来源链接、获取日期、来源类型、置信度及依据；未查找仍是“未采集”，查找无结果才写“未找到”。
- 项目读者及其关注点与输出格式，所有对象使用同一组字段。

展示组合及取舍，请用户确认该版本。此处停止；未得到明确回复前不开始候选联网搜索。用户修改后展示新版本再确认，沉默和建议选项的默认勾选不算同意。

这次确认的是候选发现前的维度草案，不是绑定最终名单的 Python DimensionLock，也不授权大规模采集。不得为了通过 guard 伪造名单批准、锁文件或维度摘要。

## 6. 联网发现四类候选并等待名单确认

仅在维度获明确确认后，使用当前宿主真实可用的搜索工具，结合项目背景、市场范围和特别说明检索。优先官方资料；第三方／用户反馈与官方宣称分开。搜索摘要只提供线索，打开支持候选分类的页面，记录真实链接及获取日期。当前无联网工具或访问失败时说明阻塞，停在发现步骤，不能用训练记忆、假 URL 或假调用ID填名单。

按四类展示候选，并保存 `projects/<项目名>/competitors.md`，状态先标“待用户确认”：

| 类别 | 识别重点 |
|---|---|
| 直接竞品 | 同一客群与核心任务争夺选择或预算 |
| 替代品 | 不同解决方式，包括人工、自建、外包及客户不买／不换的现状 |
| 潜在进入者 | 已发生进入动作与未来进入假设分开 |
| 行业标杆 | 对本项目值得学习的对象，不能因规模大就称直接竞品 |

每项列稳定ID、名称／实体、类别、分类依据、来源类型、来源链接、获取日期和待验证点。四层均检查；某层查不到写“未找到”并给搜索范围，不凑数。客户不行动等没有本次证据时标“待验证假设”，不冒充已发现的事实。检查 profile 的来源限制；不能执行的要求明确披露。

展示完整清单，请用户选取、增删或更正。此处停止，得到明确名单回复后才更新选定状态；历史已知名单不自动等于本次批准。如果名单引起字段或比较口径变化，回第5步只审阅受影响的新版本，再确认名单与维度范围一致。确认只覆盖本次展示的项目、版本和内容，修改背景或文件后重审相关范围。

## 7. 说明下一步

只有背景完整、维度和候选名单都得到明确确认，才能说明“项目初始化完成，下一步可请求 `/analyze <已确认竞品名>`”，并给一个来自已选名单的真实命令例子；不要在初始化中执行采集、分析或报告。

同时如实说明实际执行能力：当前 Python `/analyze` 仍返回 pending_module；本入口完成的是 Codex 引导初始化，不能承诺 Python 已能自动研究。现有 Python 评审 API 仍须在名单批准后生成绑定范围的正式维度提案和锁；手写的草案确认记录不能替代它，当前不自动导入这些记录或覆盖已审阅文件。

完成说明链接到本项目 profile.md、dimensions.md 和 competitors.md，概括采用的范围及未解决缺口。没有真实用户批准时保持等待，不宣布完成。
